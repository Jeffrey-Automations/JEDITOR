## U-20261115-02 · 2026-11-15 · Crash on closing the test panel after a run; empty Diff Against HEAD tab; split view font · #bugfix #ui

- **What**: three faults found while retaking the screenshots. (1) `TestPanelWidget` connected its run thread's `finished` to `deleteLater` and kept the reference, so the next `isRunning()` — closing the panel, or starting another run — reached a deleted object and took the process down with an access violation. The shell closes every view as the window closes, which turned this into a crash on exit after any test run; the thread is now released when it finishes (`_release_thread`). (2) `MultiFileDiffViewer` split a diff on `diff --git` lines only, so the editor's own diff against HEAD or the index, which has none, was dropped whole and **Tab ▸ Git ▸ Diff Against HEAD / Staged** opened an empty tab; such a diff is now one file, named from its `+++` line. (3) `SplitEditorView` took the window's interface font, and since the document is shared the main editor was redrawn in it too; it now takes the main editor's own style sheet.
- **Files**: `je_editor/pyside_ui/main_ui/test_panel/test_panel_widget.py`, `je_editor/pyside_ui/git_ui/code_diff_compare/multi_file_diff_viewer.py`, `je_editor/pyside_ui/code/split_view/split_editor_view.py`.
- **Evidence**: `test_pytest_panel.py::TestAFinishedRun`, `test_head_diff.py::TestTheViewerShowsAnEditorsOwnDiff`, `test_split_view.py::…::test_it_takes_the_main_editors_own_font_styling`; commits `4d12076`, `4b2a647`.

## U-20261115-04 · 2026-11-15 · What held the GUI thread, measured and moved off it · #perf #ui #threads

- **How it was measured**: the real window on a clone of this repository (529 widgets once every view is built), each operation timed on the GUI thread and profiled with `cProfile`, offscreen.
- **Theme switch**: 4.0–5.4 s → 0.9–1.1 s. `apply_ui_style()` called `QApplication.setStyle("Fusion")` on every switch, which re-polishes every widget (1.45 s) although the style was already Fusion; it is now set once and recorded on the application. Icons are drawn once per colour set (`lru_cache`), and the two QSS image files are written once per style. What remains is `setStyleSheet` itself (about 0.7 s), which Qt only allows on the GUI thread.
- **Git panel**: opening a repository 911 ms → 1 ms on the GUI thread. `Repo(...)`, the branches and the change list are read by `read_repository_state()` on the worker thread and shown by `_show_state()`; requests made together (`_refresh_branch_list()` then `_refresh_change_list()`) become one read, and a result for a repository replaced meanwhile is dropped.
- **Two faults in the existing background helper**, found by the new tests: a plain function connected to the worker's signal ran *on the worker thread* (the first run printed Qt's "parent's thread is … current thread is …" while a callback touched the diff view), so results now pass through a signal of the panel and arrive on the GUI thread; and finished threads were scheduled for deletion while still listed, then asked `isRunning()` — the same fault as the test panel's (U-20261115-02), fixed the same way in both.
- **Window close**: 1,040–1,460 ms → 17 ms. The terminal's shutdown called `terminate()`, which a console program on Windows never receives, and waited out 500 ms before killing; it now sends `exit` and closes the shell's input first.
- **Files**: `je_editor/pyside_ui/main_ui/shell/ui_style.py`, `shell_icons.py`, `je_editor/pyside_ui/git_ui/git_client/git_client_gui.py`, `je_editor/pyside_ui/main_ui/test_panel/test_panel_widget.py`, `je_editor/pyside_ui/main_ui/console_widget/qprocess_adapter.py`.
- **Evidence**: `test/test_git_panel_loading.py` (the read happens off the main thread; the call returns before the repository is open), `test_pytest_panel.py::TestAFinishedRun`, `test_console_adapter.py`, `test_workbench.py::TestApplyingAStyle`.
- **Open items**: `PROGRESS.md` #27 (what still runs on the GUI thread, with the numbers).

## U-20261116-01 · 2026-11-16 · The Variable Inspector shows variables · #done #ui #debug

- **What**: the inspector was always empty: its model shows the namespace it is handed, and nothing handed it one (PyBreeze #117). A window now has a `VariableHub` (`EditorMain.variable_hub`) that knows what can be looked at. The IPython console registers its in-process shell when it is built, so the table lists what was defined there, by the rule `%who` uses, and a value typed into the table is written back to the console as a literal (`ast.literal_eval`; nothing typed is run). While the debugger is paused the hub follows `DebugController`'s signals to the locals of the paused frame, asking for the stack itself when the debug panel is not open and following the frame picked there when it is; those rows are read-only. A line above the table says whose variables are shown, or how to get some.
- **Also**: the table is refreshed only while it is visible, and a refresh that finds nothing new no longer resets the model, which dropped the selection and the scroll position twice a second. Values are written with a bounded `reprlib`, so a large list or a failing `__repr__` costs neither the GUI thread nor the table.
- **Files**: `je_editor/utils/variable_inspector/variable_rows.py` (new), `je_editor/pyside_ui/code/variable_inspector/variable_hub.py` (new), `inspector_gui.py`, `main_editor.py`, `editor_widget.py`, `ipython_console.py`, the two menus that open an inspector, the four language files (3 strings), READMEs, `docs/source/docs/{Eng,Zh}/code_execution.rst`, `architecture.md`, `architecture_explore.md`.
- **Evidence**: `test/test_variable_inspector.py` (48 tests, one against a real IPython shell and one against the real debugpy adapter stopped at a breakpoint); tried in the real window with the real IPython console.
- **Open items**: a program started with Run keeps its variables in its own process and is not shown; expanding a debugger variable's children is the debug panel's job.

## U-20261116-02 · 2026-11-16 · A host decides the environment of the programs the editor starts · #done #api #process

- **What**: programs started from the editor inherited the editor's own environment (`subprocess.Popen` with no `env`). A host that sets variables for its own process handed them to the user's programs: PyBreeze's `LOCUST_SKIP_MONKEY_PATCH` made a locust script run from Run Program, Run Debugger or the shell run one user at a time (PyBreeze #120). `je_editor.set_child_environment_provider(function)` registers a function that returns the environment a child should get; `child_environment()` asks it for every start and falls back to the editor's own, logging the fault, when it raises or returns something that is not a `str` to `str` mapping. Run and its compile step, the shell, the debugger and every `LocalTaskRunner` task, the terminal (`QProcessEnvironment`) and the test panel use it. The editor's own tools (git, ruff, language servers) do not.
- **Files**: `je_editor/utils/child_process/child_environment.py` (new), `je_editor/__init__.py`, `code_exec.py`, `shell_exec.py`, `adapters/process/local_task_runner.py`, `test_panel_widget.py`, `console_widget/qprocess_adapter.py`, `docs/source/docs/{Eng,Zh}/api_reference.rst`, `architecture.md` (§6), `architecture_explore.md`.
- **Evidence**: `test/test_child_environment.py`: real child processes that do and do not see a host-only variable, the terminal's shell, and a check that fails on a `subprocess` start without `env=` in those modules. `test_public_api_contract.py` pins the two new names.
